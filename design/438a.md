# Design 438a: Legend and task templates

This task delivers the two definition views as HTML, the gate definition and the task definition, and with them the architecture that the three sibling tasks share: [`e2b6`](e2b6.md) Structural, [`44bf`](44bf.md) Status and [`9a9c`](9a9c.md) Temporal templates. Four choices shape all four designs:

- **A template takes a view model, never tablo's data and never an address.** Package `web` declares one model type per view. An adapter turns tablo's view data into the model and resolves every link through an interface the server implements. The templates then hold markup and fixed wording alone, and a test renders them from a JSON fixture with no tablo, no server and no browser.
- **Disclosure is native `details` and `summary`, as the mockups draw it.** A fold that arrives closed and whose body is costly fetches the body through HTMX on its first opening; every other fold holds its body in the page. One rule decides, and one structure describes every fold.
- **One style sheet.** It starts with the mockups' shared block byte for byte, then holds the rules two or more mockups add, then each view's own rules behind a class on `main`.
- **The mockup is the golden reference for structure, class names and fixed wording; the draft template is the authority for the bytes.** A mockup also narrates and illustrates; a template states facts as labelled fields and draws no illustration.

The drafts fix the shape. The implementation moves each to the path beside it.

### Rendering: a page, its main element, one part

```go
func New() (*Renderer, error)                                         // parses the embedded templates once
func (r *Renderer) Page(w io.Writer, p *Page) error                   // the whole document
func (r *Renderer) Main(w io.Writer, p *Page) error                   // the main element alone
func (r *Renderer) Part(w io.Writer, v View, part string, data any) error // the body of one lazy fold
```

`New` builds one template set per view: `base.html`, `partials.html` and `grid.html`, then the view's own file, which defines `body` and one `part-<name>` per lazy fold. A missing file or a parse error fails `New`, so the daemon refuses to start instead of failing a request. The three methods are the three things a response holds:

- **The full page**, for a plain request and for the export.
- **`main` alone**, the HTMX fragment for a change inside one view: a row that unfolds in a tableau, the authority filter, the server's refresh. A link that changes the view's state is a `Link` with `Swap` on; the partial `swap` adds `hx-get`, `hx-target="#main"`, `hx-swap="outerHTML"` and `hx-push-url="true"` beside the plain `href`, so the address bar holds the state and a reader without script follows the link. `Main` writes exactly the bytes of the page's `main` element.
- **One part**, the body of one lazy fold, with no `details`, no `summary` and nothing else of the page. A page renders the same `part-<name>` template in place when the fold is not lazy, so the two cannot differ.

A template error reaches the caller as the error of the method; the caller renders into a buffer and answers 500 (A1). Rendering reads no clock, no environment and no map in an order of its own, so the same `Page` gives the same bytes.

### The page

`base.html` writes what every mockup shares: `lang`, the two `meta` elements, the title `<view> · <project>`, one `link` to the style sheet, the HTMX `script` when `Page.Script` names one, the skip link, `header.site` with the navigation and the context line, `main`, and `footer.site`. `Page` carries each of these as data; [`438a/model.md`](438a/model.md) gives every field.

- **Navigation.** Ten links in the mockups' order and wording: Tableau, My corner, Queue, Blockage, Task, Assignment, Authority, History, Audit, Gates. `Views` holds the order; the current view carries `aria-current="page"`. Each link keeps the ref and the viewer and drops the focus of the page it leaves (A2).
- **Context line.** `p.context` states the parameters in force: the project, the ref with its commit and date, the viewer with the role, then each of the view's own parameters as name and value, joined by ` · `. It is the one place a page states its parameters (decision 6).
- **`main`.** `<main id="main" class="v-<view>">`, then one `h1` with the view's name and `p.question` with its question, both from VIEWS.md, then the view's `body`. `Page.Live` adds the attributes with which the server's refresh polls; they belong to task 49ce and the template writes them verbatim.
- **Footer.** One line that names the view, the project and the commit and links the gate definition. The mockups' footer names the mockup task and is theirs alone.

### Addresses

No template writes an address. An adapter builds a `Target` (a view, a task, a person, a range, the open rows, a part, an anchor) and asks a `URLs` for the address; the model then holds plain strings in `Href` fields. Task 49ce implements `URLs` for the daemon and binds one to each request, so that a link keeps the request's ref, viewer and level; task 6160 implements it for the bundle with relative paths. The query names therefore live in one place, the server, and the open point about query names in links between pages reduces to decision 7.

Every task id on every page is a link to that task's definition, with the title beside it where the place has room (`TaskRef`, partial `task`). A task in a subproject carries the junction's `url` in `Target.Project`. Emails and commit hashes are text, as in the mockups: an email in a position the `person` parameter names is `strong.mine`, and a hash is `code`.

### Symbols and their text names

Every symbol a page shows is a `Sym`: a glyph and a text name. `Legend` supplies both from the gate definition view at the commit in view, so a template holds no glyph, and a test fails on one. One rule gives the name (decision 3):

| Symbol of | Text name | Example |
|---|---|---|
| A gate | Its key | `📐` design |
| A state, a reason | Its key | `🟢` nominal, `👓` review |
| A junction mark | The method's phrase in README.md, Junctions | `🤖` an agent contributes, `👀` a reviewer accepts, `🧑` a person contributes, `🪆` a subproject does the work, `—` the gate does not apply |

The glyph always stands in `<span aria-hidden="true">`. The name follows as visible text where the place has room (partial `sym`: a status line, a row header, a summary) or as `span.sr` where it has none (partial `syms`: a cell of marks, whose names join with a comma). A legend row is the one exception in form: its glyph stands alone in `td.cell` and the row's `th scope="row"` names it. A key the legend lacks yields the key as name and no glyph, so a page never loses the word.

The self-review mark follows from the method's sentence "the reviewer is the person who accepts the work": a junction shows `👀` only where its reviewer differs from its contributor. An agent whose reviewer is the assignee, and who is the assignee, shows `🤖` alone, and the page says in words that the agent reviews its own work (decision 2).

### Disclosure

Each `details` element is a `Fold`: an `ID` unique in the page and stable across renderings, a `Class`, whether it arrives `Open`, and for a lazy fold the address of its body (`Src`) and of a page that shows it (`Alt`). The partial `fold` writes the opening tag; the view writes the `summary` first, then the body, then the closing tag.

| Class | Is | Opens by level (`ByLevel`) |
|---|---|---|
| `detail` | An item's detail: a section of a page, or one item of a list | At detail and at provenance |
| `prov` | The provenance of the item it sits in | At provenance |
| `kids` | The children of a tree node | At every level, since the tree is the glance |
| `day`, `sub` | A day of the history; a subproject's events between two pins | `day` at detail; `sub` at provenance |
| `fold` | The rest of a run under the fold rule | Never; the reader opens it |
| `group`, `columns` | A gate group of the assignment; the column choice | Never |

The levels map onto this once, for every view: **glance** is what stands outside every fold; **detail** is the body of the `detail` folds; **provenance** is the body of the `prov` folds, each nested in the detail it explains.

An `Opener` decides what arrives open. `ByLevel` is the one these tasks ship: it reads the level alone, as the table states. Task db74 replaces it with the role-specific one.

**The lazy rule.** A fold whose view names a part for it is lazy when it arrives closed and `Env.Inline` is off. `Env.Fold(class, id, part, key)` applies the rule and nothing else does. A lazy fold carries `hx-get` with `hx-trigger="toggle once"`, `hx-target="find .fold-body"` and `hx-swap="innerHTML"`, and its body is `div.fold-body` with one link, "Show this in the page", to the same page with `Target.Whole` and the fold's anchor: a page whose every fold holds its body. A fold without a part always holds its body. Each view's design lists its parts; the gate definition has none, since prototype 438a measures that a fold under about 1 KB costs more to fetch than to hold. Each model implements `Part(name, key string) (any, bool)`, which returns the value that `Renderer.Part` takes, so the server needs no knowledge of a model's fields (A3).

### Adapters

One adapter per view turns tablo's data into the model: `func <View>From(data <tablo's type>, e Env) *<View>View` in `adapt_<view>.go`. `Env` carries the `URLs`, the `Legend`, the `person` to mark, the `Opener` and `Inline`. An adapter resolves links, looks symbols up, applies the lazy rule and the fold rule, and computes the few facts a page shows that are sums or orderings of what tablo gives; each view's design names them. It derives no project fact: a fact tablo lacks is an assumption in the tables below, not adapter code.

### Two rules for lists

**The fold rule.** A stretch of more than eight consecutive rows that are alike but for the task shows its first three and folds the rest behind `details.fold`, whose summary reads "… and *n* more" and then what the rows share. `FoldRuns` applies it; a view says what "alike" means for its rows. A list of unlike rows shows every row (decision 5).

**The empty form.** A list or a table with nothing in it gives way to one `p.empty` that says in a sentence what is empty; the heading above it stays, a count in a heading reads "none", and the page keeps its chrome. No page shows an empty table (decision 4).

### Template functions and partials

Three functions: `add` (a one-based number), `plural` (one or many by a count) and `depth` (the class `d0` to `d8` of a row; a deeper row takes `d8`, and a grid row still says its true level in `span.sr`). The partials: `sym`, `syms`, `task`, `person`, `status`, `fold`, `lazy`, `swap`, `commit`, `commands`, `references`, `edge`, `junction-cells`, `event-row`. No template carries a `style` attribute, a script or an event handler, so the server may send a strict content security policy.

### The style sheet

The ten mockups share one block byte for byte, 3204 bytes between `/* shared` and `/* end shared */`, and each adds its own rules after it: 595 to 1498 bytes, 10,432 in all. [`438a/tableaud.css`](438a/tableaud.css) is the single sheet, in four parts:

1. **The shared block**, unchanged. A test holds the sheet to it as a prefix.
2. **Joined rules**: what two or more mockups add, written once. `h3`, `tbody th`, `pre`, `blockquote`, `ul.notes`, `p.key`, `p.empty`, `.proposed`, `strong.mine`, `td.cell.mine`, `.tally`, the `:target` tint, `tfoot`, the rules for tables, lists, `pre` and `code` inside `details.prov`, and the two roles of `details.detail` (below).
3. **The grid**: the rules of `table.tableau`, which the two tableaux share.
4. **Each view's own rules**, every selector behind `.v-<view>`, then one `@media (max-width: 40rem)` block.

The sheet names a colour only through the nine tokens of the shared block, which the dark scheme redefines, and it drops every rule for an illustration (`aside.illustration`, `section.illus`, `.illustrative`, `p.arrival`), since no served page illustrates.

### What later tasks may assume

**Progressive disclosure `db74`.** Every `details` has an id that is unique and stable, and a class from the table above. Every fold's arrival state comes from one `Opener`, called with the view, the class and the id, so a role-specific opener is the whole change. An open fold always holds its body. Every state inside a view has an address, built from a `Target` (`Open`, `Level`, `Whole`), and a link that changes state swaps `main`. `Grid.Control` is the column choice as a plain form; it draws nothing until db74 fills it (44bf). The templates store nothing in the browser and ship no script of their own.

**Accessibility and theming `5a2f`.** One `h1`; headings never skip a level; `lang`; the skip link first; `nav` and `main`; every table has a `caption` and a `thead` and every `th` a `scope`; every symbol is `aria-hidden` with its text name in the same block; every link has text and an address; no `style` attribute. Colour enters through nine custom properties in two blocks of one sheet, and a view's own rules sit behind `.v-<view>`. What 5a2f adds, the keyboard model, the phone layout, the `color-scheme` meta and a second cue beside a state's colour, it adds to this sheet and to `base.html`.

**Static export `6160`.** `Renderer.Page` with `Env.Inline` on, `Page.Script` empty and its own `URLs` gives a page with no script, no fetch and no absolute address.

## The gate definition

`GateView` holds four lists of `LegendRow` (gates, states, reasons, marks), the language version, the trunk, the commit that last changed each of the two files, the commands, and for the `task` parameter a `GateTask`. [`438a/gate.html`](438a/gate.html) draws five sections, each with an id other pages link to (`#gates`, `#states`, `#reasons`, `#junction-marks`, `#provenance`), and every row carries an anchor: `gate-<key>`, `state-<key>`, `reason-<key>`, `mark-<key>` with the keys `person`, `agent`, `reviewer`, `subproject` and `exempt`. A legend link from any page is `Target{View: ViewGate, Anchor: …}`, and the `:target` tint marks the row. The reserved reason carries the method's sentence as fixed text. The view has no lazy part.

## The task definition

`TaskView` holds the glance fields and six blocks. [`438a/task.html`](438a/task.html) draws `dl.fields.glance`, then one `details.detail` per block, each with its `details.prov` inside:

| Block | Fold id | Holds | Its provenance, and the lazy part |
|---|---|---|---|
| Glance | none | Task, assignee, parent and order, status, note, recorded; a `p.empty` note when the task is proposed | `prov-status`, part `status`: the status file, the deciding commit, the snapshot a recursive junction reads |
| Description | `d-about` | The description and the references | `prov-file`: the task file; no part |
| Place in the tree | `d-place` | Path, order among siblings, children with their status, authorities nearest first, authorised | `prov-authorisation`, part `authorisation` |
| Requires | `d-requires` | One row per entry: task, edge, text, the other task's status, condition | `prov-requires`, part `edges`, key `requires` |
| Dependents | `d-dependents` | The reverse relation under the fold rule; rows are alike when edge, text and condition agree | `prov-dependents`, part `edges`, key `dependents` |
| Junctions | `d-junctions` | Every gate: marks, contributor, model, reviewer, and how the junction stands | `prov-sources`, `prov-reviews`, `prov-models`, parts `sources`, `reviews`, `models` |
| Newest events | `prov-events`, part `events` | The newest five events, the count of the earlier ones, and a link to the history of the task | It is provenance itself |

The adapter computes four things. `Junction.Stands` is "does not apply" for an exempt gate, "passed" for a gate at or before the status gate ("passed, reviewed" where a review accepts it), "next" for the first applicable gate after it and "later" beyond; `Here` marks the status gate, `tr.here`. `Junctions.Key` is the marks the rows use, in the legend's order. `SourceRow.Span` groups the fields of one gate. `Dependents.Rows` is `FoldRuns` over the rows.

## What the design keeps and drops from prototype 438a

It keeps: no symbol, name, criterion or date in a template; the lazy fold as a native `details` with `toggle once` and a plain link as fallback; a fragment that holds its part and nothing else; the anchors `gate-KEY`, `state-KEY`, `reason-KEY`; the proposed note at glance; short folds in the page. It drops: the choice of mechanism per fold by size, which the lazy rule replaces; a route per fold, since a part is a parameter of the view's own route (A3); links on emails and commits, which the mockups print as text; the `folds=inline|fetch` switch, which `Target.Whole` and `Env.Inline` replace; the prototype's layout and its inline style. The prototype's finding on anchors into closed folds needs no script: the `:target` tint marks the row, and a legend row's symbol, name and key stand outside its fold.

Where a page departs from its mockup:

- **Narration and illustration.** Neither page renders the mockup's explaining paragraphs, the "two other shapes" of `task.html` (a parent and a recursive task are pages of their own, served for their ids) or the illustration of `gates.html`.
- **Representative provenance.** `gates.html` draws a provenance block on one representative gate and one reason. The page draws provenance once per table, since each entry's source is the same file and commit (decision 8).
- **The proposed note.** VIEWS.md puts the authorisation state at detail. The page also says at glance that a task is proposed, since a proposal otherwise reads as an accepted task at the level an observer sees (decision 9).
- **The parameters.** `task.html` states them in three `p.params` paragraphs; the page states them in the context line.

## Tests

All run under `go test ./...` with `html/template`, the fixtures and a parser in the test files; none needs a network, a port or a browser. The parser is the one of `prototype/5a2f/dom_test.go`, made strict: the templates close every element that is not void, and a closing tag that does not match fails the test.
