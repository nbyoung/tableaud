# Design 9a9c: Temporal templates

This task delivers the two temporal views as HTML: the history, a list of events by day, and the audit, the findings grouped by the action that resolves them. Both build on the shared architecture of [`438a`](438a.md): the page, the addresses, the symbols, the folds with the lazy rule, the empty form and the one style sheet. This document adds the two models, their templates and what is particular to them. Three choices shape it:

- **The history folds by day and does not page.** Each date is a `details.day` whose summary carries the day's counts, and a closed day is a lazy part. A range of more than fifty events arrives with every day closed, so the first page of a long history is a list of days and stays small without a cursor.
- **The history runs in author-time order, oldest first**, as VIEWS.md states and `history.html` draws, so that the status after each event builds on the line above. Tablo supplies that status; the page replays nothing.
- **The audit is one group per rule and resolver, titled by the action**, with one provenance block per group: the rule's sentence, the commits involved and the commands. Thirty findings of one rule open as one block, as `audit.html` shows.

## The model

The files: `view_temporal.go` (the models), `adapt_history.go` and `adapt_audit.go` (the adapters), `templates/history.html` and `templates/audit.html`.

### The history

`HistoryView` holds the totals, the count of each of the six kinds of event, the days and the commands. [`9a9c/history.html`](9a9c/history.html) draws:

| Part of the page | Markup | Holds |
|---|---|---|
| The off-trunk note | `p.empty` | At a ref off the trunk: the page marks each event the branch adds as a proposal |
| The summary line | `p.fold` | "*n* events in *m* commits, *first date* to *last date*:" and the count of each kind, in the order of VIEWS.md, zero included |
| A day | `details.day#day-<date>`, part `day`, key the date | The summary: the date as `h2`, and in `span.fold` the day's events, commits and the counts of the kinds present |
| An event | `li#e-<hash>-<task id>` in `ul.events`, with `details.detail#d-<hash>-<task id>` | The summary line: `span.by` the actor, `span.ev` the kind, the task as a link, and `span.what`: for a status event gate, state and reason; for a reviewed event the gate; for a pin event the `url`, the old commit when it has one, and the new; `span.proposed` on a proposal |
| An event's detail | `dl.fields` | "Status after": the status after the event, with the child a parent's roll-up comes from; the note; the effect; the model, the trailer beside the model the junction states; the committer where it differs from the author |
| A subproject's events | `details.sub#sub-<hash>-<task id>`, part `sub`, key the event's anchor; or one `p.fold` | For a pin event: the subproject's own events between the old and the new commit as a table, or "up to" the new commit for a first pin; a line that says no event lies between them when none does |
| An event's provenance | `details.prov#prov-<hash>-<task id>`, part `commit`, key the event's anchor | The full hash, the subject, author with date, committer, trailers, the files, the commands |
| The list's provenance | `details.prov#prov-list` | The `git log` commands that produce the list; no part |

The date is a heading inside a `summary`, which HTML allows, so a reader who moves by heading lands on each day. An empty range yields `p.empty` "No event in the range." and nothing else.

The adapter computes:

- **The days**: events group by author date, in the order tablo gives them. A day's `Counts` hold the kinds present; the view's hold all six.
- **One line per commit and task.** Events of one commit on one task join into one line whose `Kinds` name them in tablo's order: a commit that creates a task and authorises it reads "task, authorised".
- **The effect**, a fixed sentence by kind, and none for a kind the table omits:

  | Event | Effect |
  |---|---|
  | authorised | the task stands authorised |
  | status with the reason `review` | the hand-off: the work at the next gate waits for its reviewer |
  | reviewed | the reviewer accepts the work at the gate |
  | reviewed, where tablo says the review has no effect | no effect: the authorisation stands as the review |
  | reaffirmed | the status stands confirmed, unchanged |

- **The committer** only where it differs from the author; **the model** as the trailer states it, with the model the junction states beside it, or "none recorded".
- **The long range.** With more than fifty events in view every `day` fold arrives closed, whatever the opener says, and is therefore lazy; with fifty or fewer the opener decides, and `ByLevel` opens the days and each event's detail from detail on.

The `task`, `person` and range parameters stand in the context line. The page holds no filter form: a task's page links its own history (438a), and the address carries each filter.

### The audit

`AuditView` holds the three counts, one `FindingKind` per group for the glance table, the person with the most to resolve, the stale age, the silent rules and the groups. [`9a9c/audit.html`](9a9c/audit.html) draws:

| Part of the page | Markup | Holds |
|---|---|---|
| The counts | `p.counts` under `h2#glance` | "*n* errors, *n* warnings, *n* items of information" |
| The kinds | One table | A row per group, errors first, then warnings, then information: `span.sev` with the severity as a word and as a class, the rule, the rule's title as a link to its group, the count, the tasks, the resolver, `td.mine` where the marked person resolves |
| Most to resolve | `p` | The person with the most findings and the count |
| Silent | `ul.notes.muted` | One sentence per rule that reports nothing, as tablo states it |
| A group | `details.detail#<anchor>` under `h2#findings` | The summary: the severity, the action, the rule, the count and the resolver; then a table: Task, Gate, File, Message, Action, Resolver |
| A group's provenance | `details.prov#prov-<anchor>`, part `rule`, key the anchor | The rule and where its sentence stands, the sentence in a `blockquote`, a table of the commits involved, the commands that show and resolve the finding |

The severity is a word in a bordered `span`, and the three differ by border and weight, not by colour. A clean audit yields `p.empty`: "No finding: files and history agree at this ref. A status counts as stale after *n* days.", then the silent rules, and no findings section.

The adapter computes:

- **The groups**: findings group by rule and resolver, in the order errors, warnings, information and inside a severity in tablo's order. A group's anchor is its rule in lower case, with `-2`, `-3` for a rule's further resolvers. Its action is the finding's kind of action with a capital: Authorise, Review, Reaffirm, Record the hand-off, Clear the hand-off, Revise the file, Move the pin, Check out the submodule, the list of VIEWS.md.
- **The counts** by severity, and **the person with the most to resolve**, the first in tablo's order among equals.

The audit reads a ref, not a range, so the page carries no mark for a finding a range introduces or resolves.

### Lazy parts

| View | Part | Key | Value |
|---|---|---|---|
| History | `day` | The date | The `Day` |
| History | `sub` | The event's anchor | `*SubEvents` |
| History | `commit` | The event's anchor | The `Event` |
| Audit | `rule` | The group's anchor | The `FindingGroup` |

### What the design keeps and drops from prototype 9a9c

It keeps: a section per date; links from an event to its task; the committer and model on an event; groups keyed by the action and who takes it; the plain statement for an empty history and a clean audit; fragments that hold their part alone. It drops: the replay of statuses in the server, with its read of the whole history before a range, which tablo's data replaces (A3); the newest-first order; the `before` cursor and the "older events" link, which the days replace; the filter form and the clear links; the join of two audits on task and kind, the table of action kinds and the pattern over prose that finds a resolver, which one finding record replaces (A8); the marks `introduced`, `standing` and `resolved`, since the audit takes no range in VIEWS.md; the per-group fragment route, which the part `rule` replaces.

## Conformance to the texts

| View | VIEWS.md | Golden reference | glance | detail | provenance |
|---|---|---|---|---|---|
| History | [History](https://github.com/nbyoung/tableaux/blob/main/VIEWS.md#history) | `tableaux/docs/mockups/history.html` | Each event's summary line, under its day: actor, event, task, gate and state, or for a pin the `url` and the commits; the day's date stands in its summary | Each event's `details.detail`: the status after, the note, the model, the committer where it differs, the subproject's events between two pins | Each event's `details.prov`, and the commands that produce the list |
| Audit | [Audit](https://github.com/nbyoung/tableaux/blob/main/VIEWS.md#audit) | `tableaux/docs/mockups/audit.html` | The counts by kind, errors first, and the person with the most to resolve | Each group's `details.detail`: the findings table | Each group's `details.prov`: the rule's sentence, the commits, the commands |

The date an event shows is its day's heading; the event's own line omits it, as in the mockup. Neither view takes a window. The method does not define "a commit at a junction", on which H3 and H6 rest; this design prints the findings tablo reports and decides nothing about them.

Where a page departs from its mockup:

- **Narration and illustration.** Neither page renders the mockup's explaining paragraphs, the legend line of `history.html`, its illustrative reaffirmation, or the hand-written reasoning inside the provenance blocks of `audit.html`.
- **One picture per page.** `history.html` sets two pictures, a task and a range, on one page with a table of their parameters, and a third in `h4`; the page serves one, so the day is an `h2` and the parameters stand in the context line.
- **The effect** is one of five fixed sentences; `history.html` writes a sentence per event that names the people and the reason.
- **The audit's second section.** `audit.html` repeats the findings of one person in a table of their own; the page serves that as the audit with the `person` parameter.
- **A row per finding.** `audit.html` joins two tasks that one commit touches into one row. The page draws the rows tablo reports; `Finding.Tasks` holds several tasks when tablo joins them.

## Decisions at review

The owner decided each question this design raised on 2026-10-06, together with the cross-design rulings of that review; a decision the review did not reach stands as the design states it, accepted with the design.

1. **The order.** Accepted with the design, as stated: oldest first, as VIEWS.md and `history.html` have it. The alternative is prototype 9a9c's newest first, which suits a reader who wants only the latest and breaks the replay's reading order.
2. **Days in place of pages.** Accepted with the design, as stated: a long range arrives as closed days, each fetched on opening, and the threshold is fifty events. The alternative keeps the prototype's cursor and an "older events" link, which no mockup shows.
3. **One group per rule and resolver.** Accepted with the design, as stated: the group's title is the action. The alternative groups by action alone, as VIEWS.md's wording "by the action that resolves them" may also read, and then one group mixes rules and needs a provenance block per rule.
4. **No filter form.** Accepted with the design, as stated: the history's filters arrive by address from other pages and stand in the context line. The alternative keeps the prototype's `GET` form for task and person on the page.
5. **Fixed effects.** Accepted with the design, as stated: five sentences by kind of event. The alternative asks tablo for a sentence per event, as the mockup writes them by hand.
6. **The junction a commit is at.** Decided by the owner on 2026-10-06, from the Write commands' review (b618 decision 8): a commit that changes a status's gate is at the junction of the gate it records, and any other status commit, or a `Reaffirmed:`, is at the task's next applicable junction; README.md states it, and the history's reading of a model check and the audit's H3 and H6 follow it. An absent `person` is nobody on the history and the audit, so they show everyone (5ca9 decision 3); the audit's finding record waits for tablo's `dada` as [The plan](#implementation-notes) states, in that paragraph until the commit it must name exists, as README.md now allows.
